## 2026-10-22 — Faster YouTube catalog preparation and refresh reuse

Profiled the existing desktop/phone performance gate before editing with 80,000 saved metadata entries. First navigation was about 0.96 seconds on both viewports, with no failing release budgets. Investigation found that cooperative YouTube preparation always filtered/sorted a full replacement catalog even when only Twitch rows changed or a small live-status batch replaced a handful of YouTube cards. The synchronous selector's incremental optimization was not used by this actual navigation/preparation path.

Added a cooperative incremental shelf updater to the real prepareYoutubeSelection path. It compares immutable references, retains the exact selected array for unrelated provider changes, and merges small metadata/status replacements and appended uploads without a complete sort. The scratch change sets are capped at 4,096 relevant changes. Shrinking/reordering catalogs, corrected publication dates, newly visible interior rows, visibility-setting changes and large imports fall back to a full stable rebuild. Cancellation checks precede work and occur between short comparison/merge tasks; partial selections are not published. Unrelated Twitch refreshes now also reuse the existing format and creator indexes instead of rebuilding downstream shelves.

Cold YouTube selection now validates publication provenance once and separates known dates from an insertion-ordered unknown tail. Known dates compare numeric addedAt values without repeatedly reading provider metadata in the sort comparator. Already ordered dated runs avoid merge passes previously triggered by interleaved unknown dates. Unknown/legacy dates, strict privacy/demo/hidden/unavailable boundaries and stable equal-date ordering retain their existing semantics.

Creator indexes now record whether their latest/trending winner is unique. A creator-diverse shelf needing one card from a creator can reuse that winner rather than walk the entire historical archive. Equal-date/equal-view cases retain the seeded heap; non-finite view data disables the trending shortcut. Larger per-creator quotas still use bounded sampling. Primary requested YouTube shelves use the existing cancelable navigation scheduler after a painted frame; optional discovery continues to use background scheduling. Input leases, viewer coverage and hidden-tab gates remain in force.

Reproducible CPU benchmark: node scripts/youtube-refresh-speed-benchmark.mjs. On 100,000 YouTube rows with 20% interleaved unknown dates, five measured interleaved samples after warmup gave a median 35.36 ms for the previous selection algorithm and 21.53 ms for the new algorithm: 39% less CPU time / 1.64x throughput. An unrelated 100-row Twitch update over a combined 120,000-row catalog retained the exact YouTube selection in 6.61 ms across eight cooperative boundaries. A 48-card latest shelf used one boundary and 0.80 ms. These are deterministic CPU measurements with immediate yield callbacks, not network or full-app speedup claims.

Verification: build and typecheck pass; all 1,261 tests pass (669 scripts, 592 TypeScript). Seven new differential/performance regressions cover unknown dates/ties, status and append merges, no metadata reads for unchanged YouTube rows, fallback boundaries, cancellation, unique-winner sampling and tie behavior. Two real-store tests verify 80,000 saved YouTube rows plus 20,000 Twitch rows, exact selection/index reuse after Twitch updates, actual live-card metadata replacement, date corrections and hidden/private edits. Existing cancellation coverage now distinguishes filtering from numeric-date sorting.

Desktop/mobile browser checks pass with 80,000 persisted entries in development and production: navigation, scrolling, preview return, global search, format switches, publication labels, bounded card windows, Settings diagnostics/export and idle release/wake. Final production Home readiness was 223 ms desktop / 177 ms phone; first media navigation 858 ms / 925 ms; worst measured input-to-paint 35.5 ms / 26.2 ms; mounted cards 16 / 12; zero overflow or console/page errors. Development before/after first-navigation samples were roughly 0.90–0.98 seconds versus 0.96 seconds baseline, so these runs do not establish a broad navigation-speed percentage.
